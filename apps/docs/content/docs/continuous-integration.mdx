---
title: Continuous integration
description: Run walletwright tests on CI, headless where the wallet supports it, and cache the downloaded extensions between runs.
---

Phantom and Rabby run headless anywhere, including on a GitHub-hosted runner. MetaMask runs headless
on a developer machine but **not** on a GitHub runner, where its approvals never materialise, and
Solflare and Slush need a display everywhere. So a mixed suite is simplest to run headed under a
virtual display, which is what this project's own gate does.

## Headless

Nothing to configure: Playwright defaults to headless and the fixtures pass that through to the
wallet. walletwright launches Playwright's bundled Chromium through the `chromium` channel, because
the default headless build is the headless _shell_, which cannot load an extension at all.

```bash
pnpm exec playwright install chromium
pnpm exec tsx scripts/build-cache.ts
pnpm exec playwright test
```

A wallet with no verified headless approval flow throws at launch instead of hanging, so a mistake
here is loud.

<Callout type="warn">
  MetaMask headless is verified on a developer machine, not on a GitHub-hosted runner. MetaMask has
  documented compatibility problems running headless on GitHub Actions, and there its
  `notification.html` renders the wallet home instead of the pending request, so every approval
  times out. On that hardware run MetaMask headed, and onboard it headed too.
</Callout>

## Headed via a virtual display

The simplest thing that covers every wallet on Linux CI: install `xvfb` and run the whole suite
headed.

```bash
sudo apt-get install -y xvfb
xvfb-run --auto-servernum pnpm exec playwright test --headed
```

To keep part of the suite headless instead, pin only the specs that need a display, and drop
`--headed`:

```ts
// tests/solflare.spec.ts
test.use({ headless: false });
```

`xvfb-run` is harmless for the headless specs either way, so one command covers a mixed suite.

## GitHub Actions

```yaml
name: e2e
on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 24
          cache: pnpm
      - run: pnpm install
      - run: pnpm exec playwright install --with-deps chromium
      - run: sudo apt-get update && sudo apt-get install -y xvfb
      - run: xvfb-run --auto-servernum pnpm exec tsx scripts/build-cache.ts
      - run: xvfb-run --auto-servernum pnpm exec playwright test --headed
```

Onboard under the display too, not headless. MetaMask has documented compatibility problems running
headless on GitHub Actions, and a profile onboarded that way stays broken: its `notification.html`
then renders the wallet home instead of the pending request, even for specs that run headed.

Put `xvfb-run --auto-servernum` in front of the last step if the suite includes Solflare or Slush.

## Caching between runs

`buildCache()` re-onboards the profile each run, but it reuses the extension it already downloaded,
which is the slow part of a cold setup. Caching `.walletwright/` keeps that download between runs. The
directory holds the onboarded profile and the extensions. There are no real funds in it, but treat the
seed as a test secret.

```yaml
- uses: actions/cache@v4
  with:
    path: .walletwright
    key: walletwright-${{ runner.os }}-${{ hashFiles('wallet-setup.ts') }}
```

## Network and transaction specs

The specs that submit a transaction or switch networks also need a local chain on `127.0.0.1:8545`
with chain id `31337`: start Foundry's `anvil` directly, or via `createLocalChain()` from
`walletwright/chain` (which spawns the same binary and needs the optional `prool` peer). Without a
chain these specs fail with slow timeouts rather than skipping, so either add an anvil step before
the test run or exclude them, for example
`pnpm exec playwright test --grep-invert "network|transaction"`.

## Flakiness

MV3 service workers can be timing-sensitive on cold launches. Set Playwright `retries` (2 is plenty)
and keep `workers: 1` for wallet suites so several browsers don't contend for the machine.
walletwright already reloads patiently while it reaches the unlock screen, and waits up to 60 seconds
for an approval to render. A CI runner routes a wallet's approval page several times slower than a
developer machine, so give a wallet suite a Playwright `timeout` of at least `300_000`: a single test
can wait out two approvals, and a test timeout cuts the wait short mid-approval.
