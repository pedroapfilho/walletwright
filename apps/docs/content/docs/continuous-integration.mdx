---
title: Continuous integration
description: Run walletwright tests on CI, headless where the wallet supports it, and cache the downloaded extensions between runs.
---

MetaMask, Phantom, and Rabby run headless, so a plain `playwright test` works on a headless CI
machine. Solflare and Slush still need a real display; give those a virtual one.

## Headless

Nothing to configure: Playwright defaults to headless and the fixtures pass that through to the
wallet. walletwright launches Playwright's bundled Chromium through the `chromium` channel, because
the default headless build is the headless _shell_, which cannot load an extension at all.

```bash
pnpm exec playwright install chromium
pnpm exec tsx scripts/build-cache.ts
pnpm exec playwright test
```

A wallet with no verified headless approval flow throws at launch instead of hanging, so a mistake
here is loud.

## Headed via a virtual display

Pin the specs that need a display, so the rest of the suite still runs headless:

```ts
// tests/solflare.spec.ts
test.use({ headless: false });
```

Then wrap the run on Linux CI:

```bash
xvfb-run --auto-servernum pnpm exec playwright test
```

`xvfb-run` is harmless for the headless specs, so one command covers a mixed suite.

## GitHub Actions

```yaml
name: e2e
on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 24
          cache: pnpm
      - run: pnpm install
      - run: pnpm exec playwright install --with-deps chromium
      - run: pnpm exec tsx scripts/build-cache.ts
      - run: pnpm exec playwright test
```

Put `xvfb-run --auto-servernum` in front of the last step if the suite includes Solflare or Slush.

## Caching between runs

`buildCache()` re-onboards the profile each run, but it reuses the extension it already downloaded,
which is the slow part of a cold setup. Caching `.walletwright/` keeps that download between runs. The
directory holds the onboarded profile and the extensions. There are no real funds in it, but treat the
seed as a test secret.

```yaml
- uses: actions/cache@v4
  with:
    path: .walletwright
    key: walletwright-${{ runner.os }}-${{ hashFiles('wallet-setup.ts') }}
```

## Network and transaction specs

The specs that submit a transaction or switch networks also need a local chain on `127.0.0.1:8545`
with chain id `31337`: start Foundry's `anvil` directly, or via `createLocalChain()` from
`walletwright/chain` (which spawns the same binary and needs the optional `prool` peer). Without a
chain these specs fail with slow timeouts rather than skipping, so either add an anvil step before
the test run or exclude them, for example
`pnpm exec playwright test --grep-invert "network|transaction"`.

## Flakiness

MV3 service workers can be timing-sensitive on cold launches. Set Playwright `retries` (2 is plenty)
and keep `workers: 1` for wallet suites so several browsers don't contend for the machine.
walletwright already reloads patiently while it reaches the unlock screen, and waits up to 30 seconds
for an approval to render.
