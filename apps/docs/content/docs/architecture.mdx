---

walletwright is a small wallet-agnostic engine wrapped around one plug-in per wallet. The engine
knows how to build a cache, launch a browser from it, and drive approval popups. It knows nothing
about MetaMask, Phantom, or Slush specifically: every wallet-specific selector and flow lives behind
a single `WalletDefinition` interface. Everything you import from `@walletwright/core` is a thin
surface over that engine.

This page is the map. If you only want to write tests, [Getting started](/getting-started) and
[Examples](/examples) are enough. Read this when you want to add a wallet, add a capability, or
understand why a popup is handled the way it is.

## The layers

```
your test
   │  createWalletFixtures(setup)  /  launchWallet(setup)  /  buildCache(setup)
   ▼
public API            src/index.ts, src/fixtures.ts, src/cli.ts
   │
   ▼
engine                src/internal/{cache,launch,controller,utils,download,onboarding-patch}.ts
   │  drives, per wallet, via one interface
   ▼
wallet definitions    src/wallets/{metamask,phantom,rabby,solflare,slush}.ts  (+ src/wallets/metamask/*)
   │
   ▼
real extension        MetaMask / Phantom / Rabby / Solflare / Slush, loaded unpacked into Chromium

optional subpackages  @walletwright/core/chain (local EVM node), @walletwright/core/mock (headless provider)
```

The engine is generic. Each wallet definition fills in the wallet-specific parts (how to import a
seed, how to reach the unlock screen, which button confirms a popup). Adding a wallet means writing
one definition and registering it; the engine does not change.

## Package layout

```
packages/walletwright/src/
  index.ts            public exports
  engine.ts           buildCache(), launchWallet(): resolve the setup's wallet, run the engine
  cli.ts              `walletwright cache` command
  fixtures.ts         createWalletFixtures(), the Playwright test fixtures
  types.ts            WalletSetup, WalletDefinition, Wallet, the capability types
  chain.ts            @walletwright/core/chain entry point (local EVM node)
  mock.ts             @walletwright/core/mock entry point (headless EVM provider)
  mock-standard.ts    @walletwright/core/mock-standard entry point (headless Solana wallet)
  internal/
    cache.ts          build: onboard once, persist a profile
    launch.ts         launch: unlock a copy of the profile
    session.ts        openSession(): Chromium + extension on a throwaway profile, both phases
    profile.ts        profile keys and paths, atomic publish and recovery
    extension.ts      the extension archive a setup runs, extension-id derivation
    download.ts       fetch + extract an extension archive
    unlock-screen.ts  the shared unlock flow every wallet's unlockScreen drives
    approval.ts       createApprovals(): every approval, from the window opening to it closing
    controller.ts     createWallet(): names each wallet call and binds actions
    page-bridge.ts    installPageBridge(): connects a mock's Node handler to its in-page provider
  wallets/
    index.ts          the registry + walletKindsByEcosystem()
    metamask.ts       MetaMask definition (+ metamask/ for its flows, actions, LevelDB fix)
    phantom.ts        Phantom definition
    rabby.ts          Rabby definition

    slush.ts          Slush definition
```

## The data flow: cache, launch, drive

Three phases, each owned by one engine module. A test touches only the first (once) and the third.

```
buildCache(setup)                       once, ahead of the tests (headless ok)
  wallets[setup.wallet]                 resolved once; the engine only sees the definition
  prepareExtension  ─ download + extract the definition's source into .walletwright/
  openSession(staging)                  channel: "chromium", then prepareContext
  goto onboarding, retry until registered
  importWallet(seed, password)          the wallet's own onboarding flow
  close, finalizeCache, publish         e.g. MetaMask's LevelDB completedOnboarding
        │
        ▼   .walletwright/<profileKey>  a ready-to-unlock profile on disk
        │
launchWallet(setup, { headless }) per test worker
  openSession(copy of profileDir)       os.tmpdir()/walletwright-XXXX, cache stays pristine
  extensionIdFromPath                   derive the id, do not query the browser
  unlockScreen: reach it, type the password
  closeStrayPages                       drop about:blank and the auto-opened tab
        │
        ▼   { context, wallet }
        │
createWallet(...)                       the Wallet you drive in the test
  connectToDapp / confirmSignature / confirmTransaction / reject* / approve
  accounts.* / network.* / settings.*
```

`buildCache` is idempotent per `(wallet, version, seedPhrase, password)`: that tuple hashes to the
profile directory name (`profileKey` in `internal/profile.ts`), so re-running with the same setup
reuses the profile. Each `launchWallet` copies that profile to a throwaway directory, so
parallel workers never share a profile and the cache is never mutated. The copy is removed by the
returned `close()`, on every failure path inside `launchWallet`, and as a fallback when the context
closes.

<Callout type="info">
  Both phases launch the `chromium` channel, because Playwright's default headless build is the
  headless shell, which cannot load an extension. `buildCache` takes `{headless}` and works that way
  for every wallet; `launchWallet` takes it too and refuses it for a wallet that cannot be driven
  headless. The fixtures apply Playwright's own `headless` option only where the wallet supports it,
  which is Phantom and Rabby. See [Continuous integration](/continuous-integration).
</Callout>

## The WalletDefinition

One object per wallet describes everything the engine cannot know generically. Where the engine can
drive a step itself (downloading, unlocking), the definition declares data and the engine does the
work; the rest are functions the engine calls at the right moments. The wallet author never touches
the engine. The registry is internal: a setup names one of these built-in wallets, and adding one
means adding a definition here.

```ts
type WalletDefinition = {
  ecosystems: Ecosystem[]; // ["evm"], ["evm", "svm"], ["sui"], ...
  extensionName: string; // display name for step titles and errors, e.g. "MetaMask"
  source:
    // where the extension comes from
    | { kind: "webStore"; id: string } // the Web Store build; `version` is refused
    | { kind: "release"; defaultVersion: string; release: (version: string) => ExtensionArchive };
  onboardingPage: string; // extension-relative entry, e.g. "home.html"
  prepareContext?: (context: BrowserContext) => Promise<void>; // adjust the browser before it navigates
  importWallet: (page: Page, seedPhrase: string, password: string) => Promise<void>;
  finalizeCache?: (profileDir: string, extensionId: string) => Promise<void>;
  unlockScreen: {
    entry: string; // extension-relative page with the password field, e.g. "home.html"
    isUnlocked?: (page: Page) => Promise<boolean>; // a warm launch that comes back unlocked
    submit?: (page: Page, field: Locator) => Promise<void>; // defaults to pressing Enter
  };
  approval: {
    confirm: (popup: Page) => Locator; // every control that approves, across all screens
    cancel: (popup: Page) => Locator; // every control that rejects
    click?: { kind: "locator"; settleMs?: number } | { kind: "inPage" };
    screens?: ApprovalScreen[]; // what the wallet can put in front of the request
    urlMatch?: string; // window URL token; defaults to "notification.html"
    headless?: boolean; // its approval window surfaces as a page headless
  };
  actions?: WalletActions; // optional capabilities beyond connect/sign
};
```

| Member              | When the engine calls it                                                       |
| ------------------- | ------------------------------------------------------------------------------ |
| `source`            | in both phases, to fetch and extract the extension into the cache dir          |
| `onboardingPage`    | in `buildCache`, to navigate to the first-run screen                           |
| `prepareContext`    | in both, right after the browser starts and before anything navigates          |
| `importWallet`      | in `buildCache`, to run the import-from-seed flow                              |
| `finalizeCache`     | after `buildCache` closes the browser (profile DB not held open)               |
| `unlockScreen`      | in `launchWallet` (and `settings.unlock`), to open the home page and unlock it |
| `approval`          | in the approval engine, to find, answer, and wait out each approval window     |
| `approval.headless` | in the fixtures and `launchWallet`, to keep a wallet headed when it must be    |
| `actions`           | in the controller, to expose optional capabilities on the `Wallet`             |

### Adding a wallet

Write a definition, register it in `wallets/index.ts`, and declare the ecosystems it drives. Nothing
in the engine changes. This is the skeleton; the selectors are discovered by driving the real
extension, never guessed. Onboarding, unlock, and actions click through `clicksFor`
(`internal/click.ts`): `click` waits for a control the flow needs and throws a named error if it
never shows, and `clickIfShown` takes an interstitial that may be skipped.

```ts
// src/wallets/rabby.ts
import type { WalletDefinition } from "../types.ts";

export const rabby: WalletDefinition = {
  ecosystems: ["evm"],
  extensionName: "Rabby",

  source: { kind: "webStore", id: "acmacodkjbdgmoleebolmdjonilkdbch" },

  onboardingPage: "index.html#/new-user/guide",

  importWallet: async (page, seedPhrase, password) => {
    // drive Rabby's import-from-seed screens here
  },

  // The engine opens this page, waits past ERR_BLOCKED_BY_CLIENT, and types the password.
  unlockScreen: { entry: "index.html" },

  // The engine finds the window, clicks each control once, and waits for the window to close.
  approval: {
    confirm: (popup) => popup.getByRole("button", { name: /^(?:Connect|Sign|Confirm)$/v }),
    cancel: (popup) => popup.getByRole("button", { name: /^(?:Cancel|Reject)$/v }),
  },
};
```

```ts
// src/wallets/index.ts
import { rabby } from "./rabby.ts";

export const wallets = { metamask, phantom, slush, rabby };
```

<Callout type="warn">
  A wallet lands in the registry only once its connect and sign are verified end to end against the
  real extension. Looking done is not enough. The whole point of walletwright is that a passing test
  reflects a real extension approving a real request.
</Callout>

## The capability model

Connect and sign are universal, so they live directly on the `Wallet` and every wallet must
declare its `approval` window. Everything beyond that (managing accounts, adding networks, locking)
is optional and declared per wallet through `WalletDefinition.actions`.

```ts
type WalletActions = {
  accounts?: AccountActions; // add, switch, rename, importPrivateKey
  network?: NetworkActions; //  add
  settings?: SettingsActions; // lock, unlock
};
```

Each action receives one context object rather than positional arguments, so adding a dependency
later does not churn every wallet:

```ts
type WalletActionContext = {
  context: BrowserContext;
  extensionId: string;
  home: Page; // the wallet's own extension page, kept open after unlock
  password: string;
  unlock: () => Promise<void>; // unlock `home` through the wallet's unlockScreen
};
```

The controller mirrors whatever a wallet declares onto the runtime `Wallet` and throws a clear error
for anything it did not:

```
[walletwright] Slush does not support network.add()
```

That is the design center: the API never claims support a wallet has not proven. `network.add` is
meaningless for Slush (Sui), and Phantom's settings UI has no analogue for much of MetaMask's, so
those wallets omit the group. An undeclared call is a real gap surfaced loudly, never a silent
no-op.

### How a capability is wired

A capability method touches three places that must stay in sync:

1. the optional function on the definition side, in `WalletActions` (`types.ts`)
2. the runtime signature on the `Wallet`, in the `*Api` types (`types.ts`)
3. the binding in `createWallet` (`internal/controller.ts`)

TypeScript catches a mismatch between (2) and (3). `controller.test.ts` guards the binding to the
definition function, so a method wired to the wrong action or left unwired fails in CI rather than at
call time.

### Adding a capability to a wallet

Implement the action against the wallet's own `home` page and attach it to the definition's
`actions`. Everything drives the extension UI directly.

```ts
// src/wallets/metamask/actions/settings.ts
import { clicksFor } from "../../../internal/click.ts";
import type { SettingsActions } from "../../../types.ts";

const { click } = clicksFor("MetaMask");

export const settings: SettingsActions = {
  lock: async ({ home }) => {
    await click(home.getByTestId("account-options-menu-button"));
    // The menu renders the item several times (responsive variants), only one of which is visible.
    await click(home.getByTestId("global-menu-lock").filter({ visible: true }).first());
    await home.locator('input[type="password"]').waitFor({ state: "visible", timeout: 15_000 });
  },

  // The engine's own unlock flow, through the definition's `unlockScreen`.
  unlock: async ({ unlock }) => {
    await unlock();
  },
};
```

```ts
// src/wallets/metamask.ts
import { settings } from "./metamask/actions/settings.ts";

export const metamask: WalletDefinition = {
  // ...
  actions: { accounts, network, settings },
};
```

## The runtime controller

`createWallet` (`internal/controller.ts`) builds the `Wallet` you drive. It names each call and binds
capability actions; every approval goes to the approval engine (`internal/approval.ts`).

### The approval engine

Approval windows are the tricky part of driving a real extension. The engine owns each one from the
request to its answer, so a wallet only declares what its window looks like. Several details are
load-bearing:

- **Poll, do not wait for an event.** A window opens as `about:blank` and then navigates, so
  `context.waitForEvent('page', { url })` misses it. The engine polls `context.pages()` for a page
  whose URL matches the wallet's `approval.urlMatch`.
- **"Found" means answerable.** The window opens before it renders (a bare URL with no buttons) and
  routes to the request later, sometimes tens of seconds later under a busy MV3 service worker, and
  MetaMask's can render its home screen. The engine takes a window only once one of the wallet's
  `confirm` or `cancel` controls, or a password prompt, is showing.
- **Required vs optional.** An approval waits up to 30 seconds for the wallet-spawned window and
  throws if none appears. `connectToDapp({ optional: true })` and `approve({ optional: true })`
  wait 10 seconds and tolerate no window, because a wallet may auto-approve a site it already trusts.
- **One pass at a time, until the window closes.** Each pass answers a password prompt through the
  shared unlock flow (the same "password field cleared" check as unlock), or passes one of the
  wallet's declared `screens` (each at most once: MetaMask's Snap notice, its stale connect page), or
  clicks the next enabled control it has not clicked yet. Each label is clicked at most once, since
  Rabby re-issues a request whose control is clicked twice, and Rabby signs with Sign and then
  Confirm. The window closing after a click is the answer; one that never closes fails within 60
  seconds, naming the controls it clicked.
- **A window that closes before any click was replaced.** The wallet can close a window and open a
  fresh one for the same request, so the engine looks for the new window and answers that.
- **Clicks follow the wallet.** By default a control takes Playwright's click, optionally after a
  `settleMs` pause for a window that wires handlers late, like Slush's. Rabby declares
  `inPage`: its window unmounts while Playwright waits on a click, so the click is dispatched inside
  the page. MetaMask stays on locators, since LavaMoat scuttles `page.evaluate`.
- **Re-front the dapp.** While an extension page is the active tab, MetaMask renders new approvals
  inline there instead of opening the window the engine drives, so the dapp page goes back in front
  when an action finishes and before every approval.
- **Headless support is per-wallet.** MetaMask's approval window is created without ever being
  exposed as a page; Phantom's and Rabby's are. Only a wallet that declares `approval.headless` runs
  headless: the fixtures launch the rest headed, and `launchWallet` refuses them by name. walletwright never opens an approval
  URL itself: a page the wallet did not open for a request shows its home screen, not the request.
- **Approval windows get placed.** A window that opens partly off a small or virtual display renders
  fine but cannot be clicked, so the engine pins it to 360x592 and moves it on screen over CDP.

### Action binding

Every public method, approvals included, goes through one naming helper, so each call reaches a step
runner under its own name (`wallet.accounts.add`). The fixtures report it as a boxed Playwright step;
`launchWallet` runs it directly. Each capability method then either forwards to the declared function
(with the action context and any extra arguments) or throws a named "does not support" error. This
is why the `Wallet` surface is honest: `wallet.network.add` exists as a method on every wallet for
typing, but calling it on a wallet that did not declare `network.add` throws immediately.

## Deriving the extension id

The engine never asks the browser for the extension id (`chrome://extensions` is blocked headless
and the MV3 worker races); it computes the id from the manifest's public `key` or the absolute load
path with `extensionIdFromPath` in `extension.ts`. The derivation and the symlink caveat are covered in
[How it works](/how-it-works); what matters architecturally is that every engine module receives the
id as a plain string, so nothing downstream depends on browser state.

## The cache

`buildCache` writes an onboarded profile to `.walletwright/<profileKey>`, where `profileKey` is the
first 20 hex characters of `sha256("<wallet>:<version>:<seed>:<password>")`. Same setup, same
directory, so onboarding runs once. Change any of those four and you get a distinct profile.

`launchWallet` never launches the cached profile directly. It copies it to a fresh
`mkdtemp` directory and launches from the copy, so the cache stays pristine and parallel workers do
not share a profile. That throwaway copy has one owner, the session `launchWallet` opens: it
removes the copy on every failure path, and the returned `close()` awaits its removal after closing
the browser. The build's staging directory is owned the same way, except that it survives the close
long enough for `finalizeCache` and the publish.

## The subpackages

Two capabilities are shipped as separate entry points so the core connect/sign flow does not depend
on them. Both declare their heavy dependency as an optional peer, so a plain
`pnpm add -D @walletwright/core` pulls in neither.

### `@walletwright/core/chain`

A local EVM node for network and transaction tests. `createLocalChain()` starts Foundry's `anvil`
through `prool` and returns `{ chainId, rpcUrl, stop }`. Transaction tests need a real chain: MetaMask
reads balance, nonce, and gas off it to render the confirmation, and validates a custom network's RPC
before saving it. The default mnemonic pre-funds the same account the MetaMask setup imports, so
tests assert against a funded account with no extra step.

Needs the `prool` package and the `anvil` binary on `PATH`.

### `@walletwright/core/mock`

A headless injected-wallet fake for dapp tests that do not need a real extension.
`installMockWallet(context)` injects an EIP-1193 provider, announces it over EIP-6963, and answers
the connect/sign requests, signing with a real `viem` account so signatures verify. The provider
lives in the page but signs in Node. `internal/page-bridge.ts` connects the two for both mocks: one
Playwright `exposeFunction` binding per install, plus an init script that mounts the provider on it,
so installing twice on one context never collides. It runs in plain, even headless, Chromium in a
second or two.

It is a connect/sign stand-in, not an EVM: it does not execute transactions. For anything real, drive
an actual extension against `@walletwright/core/chain`.

Needs the `viem` package.

## Design principles

- **Verified capabilities only.** A wallet declares an action once it has been driven against the
  real extension. The registry and the API never advertise unproven support.
- **Plain `@playwright/test`.** No fork, no patched framework, no bundled runner. `@playwright/test`
  is a peer dependency, so you own the version.
- **One extension point.** A new wallet is one `WalletDefinition`. A new capability is one action
  plus its wiring. The engine is closed to change and open to extension.
- **Tested through its interface.** The engine's own tests build, launch, and approve against a
  stand-in wallet extension in headless Chromium, downloaded through the same path as a real wallet.
  The popup behaviours that once broke on CI (late routing, an idle screen, a respawned window, an
  unlock screen that needs a reload) are modes of that stand-in, not stubs of Playwright.
- **Deep modules.** The engine hides a lot of hard-won extension-automation detail behind a small
  surface (`connectToDapp`, `confirmSignature`, `approve`). Most of that detail is documented in
  [How it works](/how-it-works).
